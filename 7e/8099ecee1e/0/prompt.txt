This is some feedback around the API design:

A few things worth noting for API design:

The body field is doing a lot of work — it's markdown that contains HTML comment markers for deduplication logic, a commit SHA for anchoring, and structured finding data. If you're designing an API around this, you'll likely want to parse body into its own shape rather than passing it through raw.

There are also two finding formats in the wild — the older inline bullet style ([medium/security/single] ...) and the newer ### F-001 structured format. Any parser you build will need to handle both.

The HTML comment markers (<!-- nimbus-findings-head:{sha} -->) are essentially acting as a poor man's metadata envelope since GitHub's comment model doesn't have a native way to attach structured data. Worth thinking about whether you'd want to lift that out into a real field in your API response shape.

What do you think of this feedback for our approach:

Right, and that's actually the expected behavior given how the prompt is structured. The intent excerpts are competing for attention against diff hunks, changed files, related files, convention files — all of which are concrete code evidence. When the model has to choose between "here's a real bug I can see in the code" and "here's a labeled excerpt that might be relevant," code evidence wins almost every time.
The fundamental issue is prompt architecture
Everything is injected at the same level in one giant prompt. Intent context, diff hunks, file contents, deployment summary — it all streams in as a flat text blob. The model has no structural reason to treat Risk focus: token exposure as a directive rather than background.
There are two distinct mechanisms worth separating:
1. Pre-prompt filtering — use intent to scope what the agent sees
Before building the prompt, use the classified excerpts to actively filter and rerank what goes into changedFiles, relatedFiles, and diffHunks. If you have a Risk focus: auth token excerpt, files containing auth/token patterns should be prioritized in the context window. Files with no connection to any intent signal get deprioritized or dropped if you're hitting byte limits.
Right now context assembly and intent injection are independent. Connecting them means intent shapes what evidence the agent even sees, not just how it interprets evidence.
2. Post-output validation — check findings against intent
This is the harder enforcement mechanism but more reliable. After the agent returns findings, run a deterministic check:

For every Prohibition: excerpt, scan findings for any mention of the prohibited pattern. If none, either inject a synthetic finding or flag it in the summary.
For every Risk focus: excerpt, check if any finding touches that area. If furtherPassesLowYield is false and no finding addresses a stated risk focus, that's worth surfacing explicitly — "you flagged X as a risk area, no issues found there."
Goal signal: excerpts become a relevance filter — each finding gets a pass to check if it's connected to the goal, which feeds into the blocksGoal classification you'd add to the output schema.

None of this requires changing the model's behavior — it's deterministic post-processing on top of what you already have.
The order matters
Pre-prompt filtering improves what the agent reasons about. Post-output validation catches what it missed. Together they create a loop where intent actually controls output rather than nudging it. Right now you only have the nudge.
The practical starting point
Post-output validation against Prohibition: excerpts is the highest-leverage first move — it's deterministic, doesn't touch the prompt, and directly addresses the case where the model ignores an explicit constraint because code evidence dominated.
